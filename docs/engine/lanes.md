# /graph-ship lane detail: direct and investigate

The router (`commands/graph-ship.md` step 1) picks the lane; the engine Reads this file only when it picks one of these two. Neither opens a run dir.

- **direct** - a one-sentence diff, at most 2 files, no risk row. No run dir and no `run.json`: no nodes, no gates. Dispatch exactly one `implementer-simple` with the goal, the files and the verification it must run, working in its own worktree and branch, created through `superpowers:using-git-worktrees` from the default branch; never an inline main-session code edit, and inline work only for non-code text. Verification means running it: the repo's tests, plus a `ux-evidence` after-capture for UI or the touched Bruno request for an API. The engine reads the diff and checks the evidence file exists. An independent reviewer runs only on a risk-row match (an owner's `--lane direct` over a matched row). `ESCALATE` to `quick` when the diff grows past 2 files or crosses a risk row, the built-in `agent-control` row included: open a quick run with the goal and the partial diff as its input. It lands without asking only when `graph-control depth --root <worktree> --base <base> --profile <profile>` on its worktree reports `risk_rows: []`, `gates.auto_classes` holds `none`, and the verification is green; any matched row waits for the owner, including `agent-control` (a diff to the agent's own checks, hooks, permissions or prompts) and one an owner's `--lane direct` ran over, and a row in `gates.owner_classes` always does. It lands by the profile's `integration` mode, the `approved` and `merged` states of `<plugin-root>/docs/engine/land.md`, read at that point. Record one line in the repo's `.graph/ledger.md`: `- <UTC> direct: <goal> | files | <test command>: exit=<n> | evidence: <path> | reviewer: none|<risk row>`.
- **investigate** - a signal-driven ask ("look at the errors and fix what matters"); a lane, not a graph. One `researcher` in `signals` mode, in its own fresh context so no query output enters this one, runs the profile's `pulse.command` (none configured is NEEDS_SETUP) and writes a one-page digest to `.graph/research/pulse-<UTC date>.md`: aggregates and pseudonymised ids only, a named-user lookup only when the owner asks. The digest is working data, never committed: the fixes are the deliverable. The engine ranks the items by lane and by historical median cost (`python3 <plugin-root>/scripts/session_usage.py --medians`) and asks the owner once, unless the owner already ranked them. Each chosen item routes on its own to `direct`, `quick` or `bug`, with a run-it verification: a qa smoke test, or the signal cleared in production. "fix all" completes every item or lists each deferral with its reason.

**Host resource lanes** (the profile's `lanes:`, a different sense of the word from the router lanes above). A lane's slot count is the number of independent instances the host can run at once (simulators, emulators, local clusters, databases); it is 1 only when the evidence shows one instance, never by default when more exist. Prefer a per-task namespace over a lane: derive it from the task's `GRAPH_RUN_ID` (`<run>-t<n>`), so each task gets its own simulator clone, k8s namespace and database name, and parallel tasks never queue behind one slot. A lane is for a resource that truly cannot be multiplied. Never tell a task in its brief that it holds the whole cluster for its turn: a task that needs the whole cluster is a proving task for qa or the per-merge gate.
