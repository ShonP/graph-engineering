# /graph-ship step 9: landing approved work

The engine Reads this file at a run's merge gate, and in the `direct` lane when its change is ready to land (the `approved` and `merged` states only: `direct` has no post-deploy node). Steps 2-8 and 10 are `run.md` beside this file.

9. **After the merge gate.** Approval and merging are two ledger states. The profile's `integration: pr | push-main` (default `pr`) picks how approved work lands:
   - **`approved`** - the owner approved the merge gate, or step 5 auto-approved it.
     - `pr`: the engine pushes the run branch and opens the PR with `gh pr create` if none exists (body: the merge exhibit - diff summary, evidence, `## Follow-ups`), and records its number. Where the repo has CI, the run branch must be green before merge. When step 5 auto-approved the gate, the engine is the one that merges: `gh pr merge <n> --merge`.
     - `push-main`: from the run worktree, fetch and rebase on origin/<default>; a conflict stops and becomes a decision card. Assert the target branch: `<default>` is origin's default branch and the rebased HEAD descends from origin/<default>. Push `HEAD:<default>` (`git push origin HEAD:<default>`), find the CI run for the pushed SHA (`gh run list --commit <sha> --json databaseId`), then start `gh run watch <id> --exit-status` with run_in_background and report its result when it exits. Red CI is a decision card, never an automatic revert.
   - **`merged: <sha>`** - the change is on the default branch. The engine checks with `gh pr view <n> --json state,mergeCommit` (or, for `push-main` and off GitHub, `git merge-base --is-ancestor <run branch head> origin/<default>` after a fetch) and records the merge commit SHA, which `post-deploy` waits to see serving.

   The `post-deploy` node needs `merged:`. If the owner has not merged yet, mark it `waiting: merge` and stop; `--resume <run-id>` checks again. An empty `deploy.wait` makes its deploy checks `SKIPPED`; with no `success_signals` either, the node is `SKIPPED` and the run goes on to `retro`. A post-deploy `FAIL` is never a fix-loop input and never triggers an automatic rollback: its rollback recommendation goes to the owner at once.

   **Success signals.** The post-deploy dispatch carries `plan.json`'s `success_signals` (aggregates only). It records each signal's baseline at `deployedAt` (the merge commit's time without a deploy block) in `.graph/<run>/post-deploy/baseline.json`, and re-checks each short-window signal, one whose window closes within post-deploy's own checks, against it as a row in `post-deploy.md`. Long windows are measured later against the same baseline by `python3 <plugin-root>/scripts/measure_signals.py .graph/<run>`, triggered lazily by the SessionStart due line or at the start of the next `/graph-ship` in the repo (step 1); it writes `.graph/<run>/measure.md` as met / not met / no data. A `not met`, short-window or late, appends a line to the repo's `.graph/ledger.md` and becomes a suggested bug run: a decision card, never an automatic run or rollback. `success_signals: []` with its reason leaves nothing to check.
