# /graph-ship steps 2-8 and 10: running a playbook

The engine Reads this file once per run, before step 2, when the lane opens a run dir (`quick`, `full`, `research`, `product`). Step 1, the router, is `commands/graph-ship.md`; step 9, landing approved work, is `land.md` beside this file. Steps keep their numbers, so "step 5" means the same gate rules wherever it is cited.

2. **Open the run.** Create `.graph/<run-id>/` with a UUIDv7 id. Copy the playbook into it, so the run records which version of the graph it executed. Start `ledger.md` with the `playbook:` line first - `playbook: <name> - lane <lane>, risk: <row ids>|none - <reason>` from step 1, with `--graph` or `--lane` as the reason when the owner named it - then every node marked `pending`.

   **Control manifests.** Follow `docs/graph-controls.md`. Initialize run metadata with plugin version, graph/profile paths and required lifecycle capabilities. Complete `run.json` after the plan node produces `plan.json`, resolving its plan hash, actors, checks and baseline source. Do not invoke preflight before that plan exists. An old resumed graph missing required design, independent review or QA must be migrated explicitly and revalidated; it cannot silently call those capabilities N/A. Bind the actual copied graph path from the manifest. Missing `api` or runtime configuration for an API change is NEEDS_SETUP.

   On `--resume <run-id>`, read that ledger instead, skip nodes marked `done` or `skipped`, and resume by recomputing the ready set (step 3): `waiting: <what>` nodes are checked first, and `blocked: <what>` nodes count as `pending` and are re-run, since resuming is how the owner says the missing piece is now there.

   **Worktree.** Before the first node whose agent writes to the repo (an implementer, or qa writing a reproduction test), create the run's worktree with `superpowers:using-git-worktrees` on a branch named for the run, and pass its path to every later dispatch. Every agent that writes, writes there, with one exception.

   **Per-task worktrees.** Every implementer task gets its own worktree, cut from the run branch head at dispatch time; a plan with one task keeps the run worktree. Create each through `superpowers:using-git-worktrees` with an explicit base: `git worktree add -b <run-id>-<task> <path> <run branch head SHA>`. Task branches and the gc key on the full run id, never `<run8>`: a UUIDv7's first 8 characters are its timestamp head, so runs opened within about 65 s share them and would take each other's branches and worktrees. A host-managed worktree branches from the default branch, not the run branch, so never let the host pick the base. Run the profile's `bootstrap:` commands there, each prefixed with the task's `GRAPH_RUN_ID` (step 4). The dispatch carries the worktree path and the base SHA, and the implementer's first command is `git merge-base --is-ancestor <base sha> HEAD`; a non-zero exit is BLOCKED.

   **Merges.** A task merges into the run branch when its own fix loop exits, in completion order, from the run worktree, with `git merge --no-ff <run-id>-<task>`. Merges are serialized by the engine: tasks finishing together merge back to back and share one repo gate (step 3). On a conflict, first run `git merge --abort` in the run worktree, so later merges and the gate see a clean tree; then the conflict is a decision card (step 5) that parks that task and its dependents only, its branch is kept for resolution, and the engine continues with the next queued merge; other ready tasks keep running. After a merge, remove only that task's own worktree and branch, from the run worktree: `git worktree remove <path>`, then `git branch -d <run-id>-<task>`, never forced. Run the scoped gc only once, when no task is running (the run's end): `<plugin-root>/scripts/worktree-gc.sh --apply --base <run branch> --prefix <run-id>-`. Mid-run it is unsafe, because it removes any clean worktree behind the run branch tip, and a sibling task's fresh worktree whose implementer has not written yet is exactly that. Never run the gc unscoped: other sessions' worktrees share the repo, so its unscoped mode is a dry run for the owner.

3. **Execute the ready set.** A node is ready when every node whose `next` names it is `done` or `skipped` (the first node has none). `fix` counts as `done` only when the fix loop (step 7) exits, so `merge` never opens mid-loop. Dispatch **every ready node at once - one message, several Task calls** - then recompute the set as each finishes. In the feature playbook that sends applicable research nodes together, then `design` as soon as `research-ux` and `research-competitor` are done while tech and impact may still run, and `plan` only once all of them are. Sequential dispatch of ready nodes is the most common way this loop silently loses its value.

   **Ready queue.** The implement node schedules `plan.json`'s tasks with `graph-control ready <run>/plan.json --done <ids> --running <ids> --hold <ids> --max-width <n>`; `waves` stays a display aid only. Semaphore, not barrier: at most 4 concurrent writers. Every writer dispatch holds a slot: `implementer`, `implementer-simple`, fix rounds and remainder tasks. Reviewers and qa do not, but the host's concurrent-subagent cap (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`) binds them all, so writers plus reviewers and qa in flight must fit under it; a dispatch the host refuses waits for the next completion. Before each writer dispatch, run `graph-control host-check --root <run worktree> --profile <profile>` (its free-disk floor is the profile's `host.min_free_gb`, 20 GB when unset); BLOCKED is a decision card and that dispatch waits.

   **Task states.** The ledger keeps one state per plan task, and the state alone picks the flag it is passed under, so a started task is never offered again and a task with no writer in flight never takes a slot:

   | State | Meaning | Passed as |
   | --- | --- | --- |
   | `pending` | not started | omitted |
   | `implementing` | its `implementer`, `implementer-simple` or remainder writer is in flight | `--running` |
   | `in review` | its writer returned; its review leg is in flight, or its findings wait for the next fix dispatch | `--hold` |
   | `in fix` | a fix round (step 7) is in flight in its worktree | `--running` |
   | `merge queued` | its fix loop exited; it waits for a merge turn | `--hold` |
   | `merged, awaiting gate` | merged into the run branch; its batch gate has not passed yet | `--hold` |
   | `parked` | on a decision card: merge conflict, red batch gate, a surviving fix loop, or a writer that returned BLOCKED, NEEDS_CONTEXT or NEEDS_SETUP | `--hold` |
   | `gated` | merged and its batch gate passed, or a nothing-green `PARTIAL` (step 4) | `--done` |

   `<n>` is 4 minus the run-branch fix writers in flight (a red-gate or qa fix loop, which belongs to no plan task); held tasks are excluded from `ready` without counting against it, so parked tasks never starve the queue. A writer that returns BLOCKED, NEEDS_CONTEXT or NEEDS_SETUP is parked at once: it is passed under `--hold`, frees its writer slot, its branch and worktree are kept, the owner gets a decision card, and `ready` does not offer it again until the card is resolved. A held task does not release its dependents; only `--done` does.

   Dispatch each ready implementer with `run_in_background: true`: the engine keeps working, and the completion notification carries the child's full report, `skills_loaded:` included. On every completion notification, record it in the ledger, then recompute the ready set and fill free slots. Siblings of the same agent type share the prompt cache, so use the same agent type per size and vary only the prompt. A child's background jobs die when it ends its turn, so a brief never leaves a long command running in the background.

   Each task runs its own review leg (step 4's review depth, against that task's base), its own fix loop (step 7) in its own worktree, then merges (step 2); `reviewer-lead` panels trigger on that task's diff size. Repo gate per merge batch, in the run worktree after the merge: `graph-control check <root> --reuse` first, which replays the memoized verdict for the same tree; otherwise run the configured test through `<plugin-root>/hooks/scripts/wait-run.sh --full`. Merging into the run worktree while a gate runs there corrupts the gate, so merges queue behind a running gate, and the tasks that finished meanwhile merge together under the next one. Dependents are released only after the gate passes: the batch's tasks move from `merged, awaiting gate` to `gated`. A red gate is a decision card naming the batch (its task ids and merge commits): its tasks stay `parked`, so their dependents wait, and the default is a fix loop (step 7) on the run branch for the gate's failures, holding a writer slot; when that loop's gate passes, the batch is `gated`. Merges queue behind that loop as behind a running gate, while dispatch, review and fix of tasks that do not depend on the batch keep running. A command that uses a resource the profile declares under `lanes:` runs as `<plugin-root>/scripts/lane-run.sh <lane> --slots <n> -- <cmd>`, with the lane's declared slot count, and the brief says so; slot counts and the per-task namespace derived from `GRAPH_RUN_ID` follow the "Host resource lanes" rule in `docs/engine/lanes.md`, so a lane is only for a resource that cannot be multiplied.

   qa is batched: one qa leg per merge unit (the run, unless the plan splits it), after its last task merges; its `FAILED` rows feed a fix loop on the run branch. `implement`, `review`, `qa` and `fix` count as done when the last task merged and the qa loop exited.

   **Elapsed check.** The ledger records each writer's dispatch time, and the 45-minute time-box is measured from the engine's own dispatch time in the ledger, not the agent's self-report. A writer still running at 60 minutes shows in the status line as over budget; one that returns after more than 45 minutes without `PARTIAL` gets a ledger row `over-budget <task> <min>` for retro. The engine never kills or pre-empts an agent.

   **`when: <flag>`** makes a node conditional on a line `<flag>: yes|no - <reason>` in `goal.md`. `no` marks it `skipped (<flag>: no - <reason>)` in the ledger, and the run continues to its `next`; `yes`, or no such line, runs it - a missing flag never skips work. The plan gate's exhibit shows the line, so a wrong `ui: no` is caught before code: when the owner rejects the plan over it, set the line to `yes` in `goal.md`, mark the skipped node `pending`, run it, then re-run `plan` - no new run needed.

4. **Dispatch discipline.** For each node:
   - Resolve the agent through `localAgents` first, then the plugin roster. A node with `agent: engine` is executed by the engine, not dispatched: the engine reads the run's files and writes that node's `out:` itself.
   - For implementation and fix nodes, pick the implementer by task size from the plan: `small` -> `implementer-simple`, otherwise `implementer`. An `ESCALATE` from `implementer-simple` re-dispatches the same task to `implementer` once, without counting as a fix round.
   - **Model.** The profile's `policy.roles` is the single source of model tiers. Pass `model: <tier>` on every Agent call; the guard hook enforces it when installed. A profile without `policy:` falls back to agent frontmatter. An owner's explicit choice for this run goes in the prompt as a line `policy-override: <reason>`. Never `haiku` or `fable`, and never the `general-purpose` agent. Record requested and actual model IDs where the host exposes them; a missing or unsupported required model is NEEDS_SETUP. Independent review keeps its review tier: never substitute a cheaper reviewer.
   - Derive the REQUIRED skill list from the profile's `routing`, matched against that task's files, plus the `always` entry for the node's role (`impl` for implementers, `review` for the reviewer, `design` for the ux-designer), plus any skill the node itself names in `skills:` or `compose:` (a `compose:` skill, such as `superpowers:systematic-debugging` on the bug playbook's diagnose node, is the protocol that node follows).
   - Name every plugin skill fully qualified, as `graph-engineering:<name>`, in REQUIRED lists: a bare name can resolve to a host built-in of the same name (bare `security-review` did, in 7 of 7 measured reviews). Deduplicate the list against the selected agent's preloaded skills and the skills already loaded in that child context, comparing qualified names exactly. Name only the additional skills as non-optional; never copy full catalogs or unrelated role instructions into the prompt. Resolve applicability by changed surface and actual framework imports, not language extension alone.
   - **Skill receipt.** After a dispatch that named REQUIRED skills returns, run `graph-control skills-check --required <that list> --loaded <the child's skills_loaded: value>`; no model runs. Exit 1: mark the node `SKILLS_MISSING: <names>` in the ledger and re-dispatch once, fresh, naming them. Exit 2, a BLOCKED receipt: re-dispatch once asking for exactly `skills_loaded: <plugin>:<skill>, ...`. A second failure goes to the owner, as in step 6.
   - Name the stack id in every dispatch that may stand up `runtime`: `GRAPH_RUN_ID=<run-id>` for the `qa`-agent nodes (`qa`, `reproduce`, `verify`, `post-deploy`), `GRAPH_RUN_ID=<run-id>-design` for `design`, and for each writer dispatch `<run-id>-t<n>` (task `<n>`), `<run-id>-t<n>b` (its remainder) or `<run-id>-t<n>-r<N>` (its fix round N), so parallel writers never share a stack or wipe each other's database, and each has its own wait-run full-suite count. It goes in the prompt as text, not as an export: a subagent's Bash calls do not inherit the engine's environment, and each call is a fresh shell. The agent prefixes every runtime command with it; the profile's `${GRAPH_RUN_ID:?}` fails loudly if it is ever missing.
   - **`PARTIAL`** (fields `green_commit`, `done_cases`, `remaining_cases`, `remaining_scope`, `elapsed_min`) is not a fix round. The original task's green commit goes through review, fix and merge as usual. The engine appends task `<id>b` to `plan.json` (`depends_on: [<id>]`, the same `writable_paths`, `case_ids` = `remaining_cases`, `estimate_min` <= 45), adds `<id>b` to the `depends_on` of every other task that names `<id>` (never `<id>b` itself, which would be a cycle), so no consumer starts before the remaining cases exist, writes `tasks/<id>b.md` from the original brief plus `remaining_scope`, and, because the plan hash changed, refreshes `run.json` and re-runs `validate-plan`, `validate-briefs` and readiness preflight before the next dispatch. It logs `- <ts> PARTIAL <id> -> <id>b (<k> cases left)`. A `PARTIAL` with nothing green reports `green_commit` equal to the dispatch base SHA: the original skips review and merge, counts as merged with no change (`gated`, passed as `--done`), and `<id>b` is ready at once. For it the engine writes `findings.<id>.json` itself, in the `review-protocol` schema: `PASS`, no findings, `reviewed.base` and `reviewed.head` both the dispatch base SHA; the schema has no reviewer field, so the ledger row `- <ts> review <id> engine PASS (no change merged)` records who wrote it. Gate (b) and the retro fast path then count that task like any other. A remainder of a remainder is a decision card, never `<id>c`.
   - Pass the node's `out:` contract verbatim - it is the agent's definition of done for that node (a diagnose node's `out:` says "no fix yet"; the agent must honour it).
   - Pass the run directory, the profile path, the node's `in` artifacts, the node's `mode` if it declares one (the researcher runs one mode per dispatch), and the task's acceptance criteria, laid out in the dispatch shape below.

   The agent never chooses its conditional skills. That decision lives here, because an agent that picks can quietly skip loading and write from priors instead.

   **Dispatch shape.** A dispatch has five parts only: (1) where the task fits: run dir, profile path, node, worktree path and base SHA, plus the lines the bullets above resolve (REQUIRED skills, `GRAPH_RUN_ID`, `mode`, the `out:` contract); (2) the brief path `.graph/<run>/tasks/<n>.md`, which carries the `in` artifacts and acceptance criteria (for a node that is not a plan task, `<n>` is the node name and the engine writes the brief); (3) interfaces from earlier tasks; (4) resolved ambiguities; (5) the report path. Never paste history: no transcript, no earlier child's prose, nothing a path can carry. Every Agent `description` starts with `<first 8 chars of run id>:<node>`, for example `0192f3ab:review`; the status line groups by it.

   **When to delegate.** Delegate when the main context is above ~150k, when independent lanes exist, when independence is required (review, qa), or when the work runs over ~15 minutes or needs a long suite. Work inline only when the context is under ~100k, the change touches at most 2 files, takes fewer than 5 tool calls, runs no long suite, and is a non-code text change; code always goes to an implementer. Inline work that touches a risk row (auth, data schema, API surface, infra, outbound sends, spend, destructive commands) still gets a scoped reviewer. Spawn a child only for at least 2 concurrent independent parts that each need ~10+ tool calls, or where independence is required.

   **Review depth.** Before each review leg (every task's, and every re-review), run `graph-control depth --root <run worktree> --base <run base> --profile <profile> --plan <run>/plan.json` and write its `depth`, `risk_rows` and reasons to the ledger; a task's leg runs it with `--root <task worktree> --base <task base sha>`. The depth picks the leg:
   - `lint` (prose only, outside `instructionPaths`, no risk row, so never `agent-control`): no reviewer is dispatched. The engine runs the scripted checks itself: the repo's `lint.argv` from `.claude/graph-checks.json` (the nearest one, run from its directory) on each changed file with a listed extension; with no lint block, the depth verdict is the only check. It writes `findings.json` itself, as that task's `findings.<task>.json` (step 7), in the `review-protocol` schema: `PASS` with no findings when every command exits 0, otherwise one `important` finding per failing file (rule `lint`, route `patch`) with the output tail. It records the review receipt as the engine's own actor: before recording, it rebinds the manifest's review check to that `depth` command (kind `analysis`) and the review actor to the engine session, which never implemented, with `executed` the changed-file count and the counts from `findings.json`. A fix round reruns depth, so code in the fix makes the next leg `single` or `panel`.
   - `single`: one `reviewer`.
   - `panel`: the lead rule below.

   **Leads.** qa: one surface gets one `qa`; 2 lanes, 2+ platforms, or ~8+ criteria with 3+ lanes get `qa-lead`, which stands the runtime up once, runs the lane leaves and runs `down` last; the engine never leads qa leaves itself. Review: a `graph-control depth` panel with more than ~2,000 changed lines or ~120k diff tokens gets `reviewer-lead`; any other panel gets one reviewer with an explicit lens list and mandatory blocker reproduction. Leads are dispatched only at depth 1, and leaves never have the Agent tool. A lead runs its children in the foreground, since a background child is re-woken only when its lead is idle. The owner's settings pin `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2`, which `/graph-init` proposes. The ledger copies each lead's returned child ids and report paths.

   **Failures.** On a transient 5xx, 529 or 429, re-dispatch the task fresh from on-disk artifacts (its brief, partial report and diff), at most 3 attempts, one ledger row each. On the first 429, stop new fan-out, checkpoint the ledger, notify the owner with the reset time when the error states one, and resume with `--resume <run-id>`. No heartbeat nudges: stalled agents show in the status line (`graph-control status --line`).

   **Estimate and actuals.** At the plan gate, print one line: agents by role times the role medians from `python3 <plugin-root>/scripts/session_usage.py --start <30 days ago> --end <now> --medians` (the last 30 days), plus wall time from the `critical_path` that `validate-plan` prints, as `estimate: <n> implementer, <n> reviewer, <n> qa = <tokens>; critical path <d>, ~<hours> h wall time`. At the merge gate, `merge.md` prints the actuals from the same script with `--run <run8>` over the run's window. Actual tokens or wall time over 2x the estimate opens a decision card.

   **Before implementation.** Run `validate-plan <run>/plan.json` and `validate-briefs <run>` (each task's `tasks/<id>.md`: present, at most 300 lines, at most 35% fenced code), complete the bound run manifest, then run `preflight <run>/run.json --profile <profile> --graph <run>/graph.md --readiness-only`. Planning and its prerequisite research/design produce these inputs; implementation cannot start until all three validators pass, and a BLOCKED brief goes back to the planner. Dispatch consumers only after their producers' contract checks pass. Record each check through `record-receipt <run>/run.json <receipt.json> --store <run>/receipts.json`; before presenting the merge gate, run `verify <run>/run.json --store <run>/receipts.json`. Commands use `uv run <plugin-root>/scripts/graph-control.py`. Receipts must bind the exact revision and dirty tree, runtime/fixtures/schema and executed cases; a source or contract change invalidates affected evidence. Reviewer and QA identities must be independent of implementers. Required test reports must include assertions and all expected case IDs with no skipped required cases.

5. **Honor gates.** `gates.plan` and `gates.merge` take only `owner` (doctor flags any other value), so no gate is skipped by configuration; only the merge gate can open without the owner, by the class rule below. A node with `gate: yes` stops and presents, for the owner's approval before anything downstream runs: its artifact; the ledger's `playbook:` line (which playbook, and why); at the plan gate, `goal.md`'s `ui:` line and - when `design` ran - the plan's `## Experience` section with its as-is and to-be images shown, not linked, since this is where the owner approves where things go, plus any interactive render it names. When the designer left `design/claude-design-brief.md` and this session has a Claude Design connector (tools named `mcp__claude_ai_Claude_Design__*` or `mcp__claude-design__*`), run the brief, link the canvas in the exhibit and add the link to `design/experience.md` before the first UI task commits it; otherwise say it was skipped; and at the merge gate, qa's verdict line verbatim - `PASS`, or `PASS (static-only)` with the skipped live steps listed, so an infra run verified without a cluster never looks like one verified with one.

   **Merge exhibit.** The merge node is `agent: engine`: the engine renders the exhibit itself into `.graph/<run>/merge.md`, with no planner dispatch. It holds the change digest, the output of `graph-control digest --root <run worktree> --base <run base> --plan <run>/plan.json --profile <profile>` as printed (at minimum the diff summary: `git diff --stat <base>..HEAD` grouped by plan task, using each task's `writable_paths` from `plan.json`); the review and qa verdict lines verbatim; the ux-evidence before/after pairs inline, when the run has them; `followups.md` as `## Follow-ups`; and what was parked (blocked legs, findings that survived the fix loop, skipped nodes with their reasons). The same file is the PR body in step 9.

   **Decision cards.** A question for the owner is a card, not a blocking ask. Append it to `.graph/<run>/decisions.md`, one line each: `- [ ] D<n> <what> | why owner: <..> | default: <..> | cost of waiting: <..> | reversible: yes|no | meanwhile: <..> | redo if other: <..>`. For a reversible card, apply the default, mark it `- [x] ... (default applied)`, and keep running. For an irreversible card, park only that leg; every other ready node keeps running. Read owner context lazily, only when a question is about to go to the owner. When the profile sets `ownerAccess: <path>`, inject that file into planner and spike briefs. Ask first, always, for spend, public posting, deletion, production writes, destructive operations, credentials, the first publish of a new public page, and messages to real people.

   **Gates by class.** `gates.owner_classes` and `gates.auto_classes` name risk row ids, plus `none` for a diff that matches no risk row. The merge gate is auto-approved only when all four hold: (a) every risk row reported by `graph-control depth --root <run worktree> --base <run base> --profile <profile> --plan <run>/plan.json` (JSON field `risk_rows`, which carries `outside-the-run` when a changed path matches no task's `writable_paths`; treat an empty list as `none`) is in `auto_classes` and none is in `owner_classes` or is `agent-control`; (b) `graph-control findings <run>/findings.json <run>/qa-findings.json --counts` returns blocking 0 and important 0, where `<run>/findings.json` stands for every task's latest `findings.<task>.json`, one path each (an absent file is BLOCKED, not zero; a nothing-green `PARTIAL` has its engine-written file, step 4); (c) qa's verdict is a full PASS, and `PASS (static-only)` from an infra run without a throwaway cluster does not qualify; (d) `verify` passes. `agent-control`, the built-in control-plane row (`.claude/**`, `CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `.github/**` and `instructionPaths`), always waits for the owner, even under `--auto-merge`: that diff can rewrite the checks, hooks, permissions and gates this very rule reads. The template default for `auto_classes` is `[]`, so the owner merges everything until a repo opts in. `merge.md` records which condition held or failed.

   `--auto-merge` keeps its per-run meaning: it relaxes only the merge gate, only for this run, whatever the classes except `agent-control`, and only when (b), (c) and (d) hold.

   **Notifications.** If the host exposes a push-notification tool, send only on transitions (NEEDS YOU becomes non-empty; run finished or failed; first 429), and only from a turn that already happens; never start a turn to notify.

6. **Handle NEEDS_SETUP.** If an agent reports it, stop that leg and tell the owner which skill or dependency is missing. Do not re-dispatch without it, and do not let the agent improvise the competency. A result produced without the house patterns looks the same as one produced with them, which is precisely the danger.

7. **Fix loop.** The fix node takes every input the two legs produce: each blocking and important finding in the reviewer's `findings.json` and in qa's `qa-findings.json` (for example Schemathesis spec drift), and each `FAILED` qa row (its reproduction steps are the bug report). Round files are per task, since parallel tasks review at once: a task's review findings live at `.graph/<run>/findings.<task>.json` (the engine names that path in the review dispatch), and before each re-run the round is kept as `findings.<task>.r<N>.json`, round 1 = that task's first review. qa keeps `qa.md`, `qa-findings.json` and `qa*.r<N>.*` at run level (one batched leg, step 3). So the next round writes fresh files and `retro` can see what every round caught, not only what survived. After each review or qa round, the engine appends each blocking or important finding's class, its `rule`, to `.graph/<run>/classes.md` as `- <class> | <finding id> | <task> round <n>` (qa rows use `qa` as the task): deterministic, no dispatch. That path goes to every later dispatch in the run, so a fix round or a later task sees the classes this run already hit. Each round is a FRESH dispatch of the tier that built the task, never a resumed agent, in that task's worktree (a qa fix loop works on the run branch) and holding a writer slot (step 3): its inputs are the brief, the findings file paths and `git diff <last reviewed head>..HEAD`. SendMessage the original author only for findings marked `needs_author_context: true` (the field arrives with the findings schema in `review-protocol`). Round 3 moves up one tier: a small task goes to `implementer`, and a standard task stays on `implementer` but requires a fresh diagnosis first (`superpowers:systematic-debugging` REQUIRED, a new hypothesis in `attempts.json` before any edit). Then re-run every node that feeds `fix` - the reviewer's node, whose input is the open blocking and important findings plus the fix-commit diff, not the whole branch, and the qa-agent node (`qa`, or `verify` in the infra playbook) for the rows that failed, any row whose files the fix touched, and every check that produced a finding in the previous round's `qa-findings.r<N>.json` (Schemathesis drift re-runs Schemathesis) - so the fresh `qa-findings.json` says whether each one is gone rather than silently dropping it. At most 3 rounds. Record each attempted fix, hypothesis, evidence and result in `attempts.json`; run `validate-attempts` before another attempt. Two failed attempts on the same hypothesis require fresh diagnosis or a plan change before continuing. Do not repeat the same command or broaden tests without a changed input, a failure to investigate or unresolved evidence. Surface anything that survives as a labelled list for the owner. Nits never block.

   A repo whose profile sets `runtime.none` still runs the qa node; qa verifies through the public surface instead of a stood-up stack, so this rule does not trap libraries and CLIs. A qa `BLOCKED` is not a fix-loop input: the system could not be stood up, which is a missing `runtime` block, seed or env, not a code defect. Treat it like `NEEDS_SETUP` (step 6) and name what is missing. The merge gate does not open on a run whose qa leg never ran. A `design` node's `BLOCKED` (a configured `runtime` that would not come up for the as-is captures) is handled like `NEEDS_SETUP` (step 6) too: mark it `blocked: <what>`, tell the owner what is missing, and `--resume` re-runs it - never design blind, and never let `plan` run without it.

8. **Keep the coordinator compact.** Children write full logs and findings to artifacts and return at most 1,500 tokens plus artifact paths: status, source identity, changed case results, blocker. A reviewer returns one verdict line plus the findings path. The engine reads files and never relays a child's prose into another dispatch; the next dispatch gets the path. A child that is only waiting never messages main, and the engine does not reply to one. Coalesce repeated running/progress/yielded notifications by task and event ID; update status without a new reasoning turn where the host supports it. Wake the coordinator for completed, failed or decision-required events. Host-mandated wakeups may still occur; record them as overhead rather than claiming suppression. Reuse accepted evidence by exact source/contract identity; never copy the entire session into a child.

   **Update the ledger after every node:** status, artifact path, timestamp. Follow-ups live beside it in `.graph/<run>/followups.md` (written by the plan node, appended by implementers); the engine never rewrites that file, and the merge node reads it. This is what lets a run survive compaction and what `--resume` reads. Trust it over your own recollection of what you did.


10. **Retro, then report.** Retro fast path: when every task's findings files (`findings.<task>.json` and each `findings.<task>.r<N>.json`) and qa findings files (`qa-findings.json` and each `qa-findings.r<N>.json`) hold zero blocking or important findings (each file present; an absent file is not zero findings), no qa row was `FAILED` in any round, no `NEEDS_SETUP` or `BLOCKED` stop happened, and post-deploy is not `FAIL`, the engine writes a one-line `.graph/<run>/retro.md` - `No leaks: <n> review rounds, <m> qa rows verified` - marks the retro node `done (fast path)` and dispatches nothing. Otherwise it dispatches the `retro` agent.

    **Report.** The full report goes to `.graph/<run>/run-report.md` (not `report.md`, which is the bug playbook's input): the run id, each node's status, the gate verdicts, the post-deploy verdict, and the retro's proposed rule changes as diffs for the owner to apply or decline. The engine applies none of them. Deliverables go to a durable repo path, never only to chat or a scratchpad.

    **Reply contract.** Status and decision replies to the owner take at most 5 lines, in plain words, echoing the owner's choices back: what I did, what I need from you, and one recommended action. No internal codes, node ids or SHAs unless asked; point to the report for the rest.
