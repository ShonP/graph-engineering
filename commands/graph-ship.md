# /graph-ship - the engine

Execute a playbook. **The engine is playbook-agnostic:** it reads `graphs/<name>.md` and runs whatever nodes it finds. It does not know what a feature is. That is what lets the same engine run `feature`, `bug` and `infra` without a branch per workflow here.

## Steps

1. **Load context, then route.** Read the candidate repository's `.claude/graph-profile.yaml` first; in a multi-repo workspace, its repo-relative runtime and API settings take precedence over workspace routing defaults. If absent, tell the owner to run `/graph-init` and stop. The router below runs inline in this turn: no skill load, no dispatch. Detail that only one lane needs lives in that lane's graph file, read only when the lane runs.

   **`--resume <run-id>`: no routing.** Read the playbook copy in `.graph/<run-id>/` and the ledger's `playbook:` line; the run finishes on the lane and graph it started with.

   **Split, then match risk.** An ask with several independent goals splits into parallel runs, one per goal, each routed on its own. Nothing is deferred silently: a goal not started now is named back to the owner with the reason. Then read the profile's `risk:` rows (`id`, `paths` globs, `keywords`). A row matches when one of its keywords appears in the goal text, or one of its path globs matches a file the goal names. Any match forces at least `quick`. A profile with no `risk:` block matches nothing, and the ledger line says so.

   **Lanes.** Pick the lane by size and risk first; the ask type only picks the graph. `--lane` and `--graph` are the owner's explicit choice and win over the pick; `--graph` still forces a playbook (its lane is `quick` for `graphs/quick.md`, `full` otherwise).
   - **answer** - a pure question or a current-state fact; no run dir. A current-state fact (a version, a price, a model, live data) needs a lookup, one WebFetch or one `researcher` dispatch, never memory. Name the source in the reply.
   - **direct** - a one-sentence diff, at most 2 files, no risk row. No run dir and no `run.json`: no nodes, no gates. Dispatch exactly one `implementer-simple` with the goal, the files and the verification it must run, working in its own worktree and branch (step 2's worktree rule); never an inline main-session code edit, and inline work only for non-code text (step 4). Verification means running it: the repo's tests, plus a `ux-evidence` after-capture for UI or the touched Bruno request for an API. The engine reads the diff and checks the evidence file exists. An independent reviewer runs only on a risk-row match (an owner's `--lane direct` over a matched row). `ESCALATE` to `quick` when the diff grows past 2 files or crosses a risk row: open a quick run with the goal and the partial diff as its input. It lands through step 9's `integration` mode without asking only when step 5's rule (a) holds with no plan: `graph-control depth --root <worktree> --base <base> --profile <profile>` on its worktree reports `risk_rows: []`, `gates.auto_classes` holds `none`, and the verification is green; any matched row waits for the owner, including one an owner's `--lane direct` ran over, and a row in `gates.owner_classes` always does. Record one line in the repo's `.graph/ledger.md`: `- <UTC> direct: <goal> | files | <test command>: exit=<n> | evidence: <path> | reviewer: none|<risk row>`.
   - **quick** - a defined intent, at most 5 files, or any risk row on a small ask. Runs `graphs/quick.md` through steps 2 to 10 like any playbook.
   - **full** - anything larger: `graphs/feature.md`, `bug.md` or `infra.md`, picked by the triage below.
   - **spike** - a "can X do Y" question with a falsifiable answer: the researcher's `spike` mode, dispatched as one `graph-engineering:researcher-spike`, no run dir, its report at `.graph/research/<slug>.md`. That agent runs without CLAUDE.md, so its brief carries the profile path, the REQUIRED skills, the rule packs and the project invariants (stack, paths, commands, what must not be touched).

   Research and product asks (a comparison, a decision, "is this worth building"): until the research playbook lands, dispatch the `researcher` in `tech` or `competitor` mode at depth 1 and write to `.graph/research/<slug>.md`. Like `answer`, `direct` and `spike`, they are exempt from `run.json` controls.

   **Triage (`full` lane, no `--graph`).** Classify the goal and pick one playbook:
   - **bug** - the goal describes existing behaviour that is wrong: an error, crash, regression, wrong result, a failing check, a stack trace, an issue labelled bug.
   - **infra** - the goal's target is deployment configuration only: Helm charts or values, kustomize overlays, Argo CD applications, Kubernetes manifests, gateway or policy resources, secrets wiring, cluster add-ons - and no application code.
   - **feature** - everything else, including chores and refactors (the planner scales the plan down) and changes that touch both app code and infra (the impact map classifies the infra tasks).

   When two fit, prefer the narrower one only if the goal says so outright; otherwise `feature`. Carry the lane, the matched risk rows, the playbook and a one-line reason into step 2, which writes them as the first line of `ledger.md` (`playbook: bug - lane full, risk: none - "checkout returns 500 when the cart is empty" describes wrong behaviour`). Never ask before running: a question costs the owner's attention on every run. In `full` the triage line heads the plan gate's exhibit, so a wrong playbook is caught before any code and the owner reruns with `--graph`. In `direct` and `quick` the run-it verification is the catch: tests, the after-capture and the Bruno request run the change, and `ESCALATE` moves work up a lane. Every playbook gates before its first code-writing node (`quick`, feature, bug and infra all gate at `plan`); a playbook added later must too, or the router must ask the owner before running it.

2. **Open the run.** Create `.graph/<run-id>/` with a UUIDv7 id. Copy the playbook into it, so the run records which version of the graph it executed. Start `ledger.md` with the `playbook:` line first - `playbook: <name> - lane <lane>, risk: <row ids>|none - <reason>` from step 1, with `--graph` or `--lane` as the reason when the owner named it - then every node marked `pending`.

   **Control manifests.** Follow `docs/graph-controls.md`. Initialize run metadata with plugin version, graph/profile paths and required lifecycle capabilities. Complete `run.json` after the plan node produces `plan.json`, resolving its plan hash, actors, checks and baseline source. Do not invoke preflight before that plan exists. An old resumed graph missing required design, independent review or QA must be migrated explicitly and revalidated; it cannot silently call those capabilities N/A. Bind the actual copied graph path from the manifest. Missing `api` or runtime configuration for an API change is NEEDS_SETUP.

   On `--resume <run-id>`, read that ledger instead, skip nodes marked `done` or `skipped`, and resume by recomputing the ready set (step 3): `waiting: <what>` nodes are checked first, and `blocked: <what>` nodes count as `pending` and are re-run, since resuming is how the owner says the missing piece is now there.

   **Worktree.** Before the first node whose agent writes to the repo (an implementer, or qa writing a reproduction test), create the run's worktree with `superpowers:using-git-worktrees` on a branch named for the run, and pass its path to every later dispatch. Every agent that writes, writes there, with one exception.

   **Per-task worktrees.** A wave, or a fix round, with 2+ writers running at once gives each task its own worktree; a single-writer wave keeps the run worktree. Create each through `superpowers:using-git-worktrees` with an explicit base: `git worktree add -b <run8>-<task> <path> <run branch head SHA>`. A host-managed worktree branches from the default branch, not the run branch, so never let the host pick the base. Run the profile's `bootstrap:` commands there, each prefixed with the task's `GRAPH_RUN_ID` (step 4). The dispatch carries the worktree path and the base SHA, and the implementer's first command is `git merge-base --is-ancestor <base sha> HEAD`; a non-zero exit is BLOCKED. After each such wave or fix round, merge the task branches into the run branch in plan order, from the run worktree, each with `git merge --no-ff <run8>-<task>`; a conflict becomes a decision card (step 5) and the next wave waits. Then, still from the run worktree, remove this run's merged task worktrees: `<plugin-root>/scripts/worktree-gc.sh --apply --base <run branch> --prefix <run8>-`. Never run the gc unscoped: other sessions' worktrees share the repo, so its unscoped mode is a dry run for the owner.

3. **Execute the ready set.** A node is ready when every node whose `next` names it is `done` or `skipped` (the first node has none). `fix` counts as `done` only when the fix loop (step 7) exits, so `merge` never opens mid-loop. Dispatch **every ready node at once - one message, several Task calls** - then recompute the set as each finishes. In the feature playbook that sends applicable research nodes together, then `design` as soon as `research-ux` and `research-competitor` are done while tech and impact may still run, and `plan` only once all of them are. Sequential dispatch of ready nodes is the most common way this loop silently loses its value.

   **Implementation waves.** The implement node runs `plan.json`'s tasks in the waves `graph-control waves <run>/plan.json --max-width <n>` prints, where `<n>` is at most 4 concurrent opus writers. Before each wave, run `graph-control host-check --root <run worktree> --profile <profile>`; BLOCKED becomes a decision card and the wave waits. Dispatch every task of a wave in ONE message, each Agent call with `run_in_background: false`: the calls run concurrently, and siblings of the same agent type share the prompt cache, so use the same agent type per size and vary only the prompt. A child's background jobs die when it ends its turn, so a brief never leaves a long command running in the background.

   No pipelining: each wave runs its own review and qa legs and fix loop (step 7) over that wave's diff, and a dependent wave waits until the previous wave's fix loop exits. Step 7's round numbers continue across waves, so no wave overwrites another's findings files; `implement`, `review`, `qa` and `fix` count as `done` only after the last wave's loop. The repo gate runs once per wave, in the run worktree after the merge: `graph-control check <root> --reuse` first, which replays the memoized verdict for the same tree; otherwise run the configured test through `<plugin-root>/hooks/scripts/wait-run.sh`. A command that uses a resource the profile declares under `lanes:` runs as `<plugin-root>/scripts/lane-run.sh <lane> --slots <n> -- <cmd>`, with the lane's declared slot count, and the brief says so.

   **`when: <flag>`** makes a node conditional on a line `<flag>: yes|no - <reason>` in `goal.md`. `no` marks it `skipped (<flag>: no - <reason>)` in the ledger, and the run continues to its `next`; `yes`, or no such line, runs it - a missing flag never skips work. The plan gate's exhibit shows the line, so a wrong `ui: no` is caught before code: when the owner rejects the plan over it, set the line to `yes` in `goal.md`, mark the skipped node `pending`, run it, then re-run `plan` - no new run needed.

4. **Dispatch discipline.** For each node:
   - Resolve the agent through `localAgents` first, then the plugin roster. A node with `agent: engine` is executed by the engine, not dispatched: the engine reads the run's files and writes that node's `out:` itself.
   - For implementation and fix nodes, pick the implementer by task size from the plan: `small` -> `implementer-simple`, otherwise `implementer`. An `ESCALATE` from `implementer-simple` re-dispatches the same task to `implementer` once, without counting as a fix round.
   - **Model.** The profile's `policy.roles` is the single source of model tiers. Pass `model: <tier>` on every Agent call; the guard hook enforces it when installed. A profile without `policy:` falls back to agent frontmatter. An owner's explicit choice for this run goes in the prompt as a line `policy-override: <reason>`. Never `haiku` or `fable`, and never the `general-purpose` agent. Record requested and actual model IDs where the host exposes them; a missing or unsupported required model is NEEDS_SETUP. Independent review keeps its review tier: never substitute a cheaper reviewer.
   - Derive the REQUIRED skill list from the profile's `routing`, matched against that task's files, plus the `always` entry for the node's role (`impl` for implementers, `review` for the reviewer, `design` for the ux-designer), plus any skill the node itself names in `skills:` or `compose:` (a `compose:` skill, such as `superpowers:systematic-debugging` on the bug playbook's diagnose node, is the protocol that node follows).
   - Name every plugin skill fully qualified, as `graph-engineering:<name>`, in REQUIRED lists: a bare name can resolve to a host built-in of the same name (bare `security-review` did, in 7 of 7 measured reviews). Deduplicate the list against the selected agent's preloaded skills and the skills already loaded in that child context, comparing names with the prefix stripped. Name only the additional skills as non-optional; never copy full catalogs or unrelated role instructions into the prompt. Resolve applicability by changed surface and actual framework imports, not language extension alone.
   - Name the stack id in every dispatch that may stand up `runtime`: `GRAPH_RUN_ID=<run-id>` for the `qa`-agent nodes (`qa`, `reproduce`, `verify`, `post-deploy`), `GRAPH_RUN_ID=<run-id>-design` for `design`, and `GRAPH_RUN_ID=<run-id>-t<task number>` for each implementer task, so parallel tasks never share a stack or wipe each other's database. It goes in the prompt as text, not as an export: a subagent's Bash calls do not inherit the engine's environment, and each call is a fresh shell. The agent prefixes every runtime command with it; the profile's `${GRAPH_RUN_ID:?}` fails loudly if it is ever missing.
   - Pass the node's `out:` contract verbatim - it is the agent's definition of done for that node (a diagnose node's `out:` says "no fix yet"; the agent must honour it).
   - Pass the run directory, the profile path, the node's `in` artifacts, the node's `mode` if it declares one (the researcher runs one mode per dispatch), and the task's acceptance criteria, laid out in the dispatch shape below.

   The agent never chooses its conditional skills. That decision lives here, because an agent that picks can quietly skip loading and write from priors instead.

   **Dispatch shape.** A dispatch has five parts only: (1) where the task fits: run dir, profile path, node, worktree path and base SHA, plus the lines the bullets above resolve (REQUIRED skills, `GRAPH_RUN_ID`, `mode`, the `out:` contract); (2) the brief path `.graph/<run>/tasks/<n>.md`, which carries the `in` artifacts and acceptance criteria (for a node that is not a plan task, `<n>` is the node name and the engine writes the brief); (3) interfaces from earlier tasks; (4) resolved ambiguities; (5) the report path. Never paste history: no transcript, no earlier child's prose, nothing a path can carry. Every Agent `description` starts with `<first 8 chars of run id>:<node>`, for example `0192f3ab:review`; the status line groups by it.

   **When to delegate.** Delegate when the main context is above ~150k, when independent lanes exist, when independence is required (review, qa), or when the work runs over ~15 minutes or needs a long suite. Work inline only when the context is under ~100k, the change touches at most 2 files, takes fewer than 5 tool calls, runs no long suite, and is a non-code text change; code always goes to an implementer. Inline work that touches a risk row (auth, data schema, API surface, infra, outbound sends, spend, destructive commands) still gets a scoped reviewer. Spawn a child only for at least 2 concurrent independent parts that each need ~10+ tool calls, or where independence is required.

   **Leads.** qa: one surface gets one `qa`; two lanes get two `qa` leaves dispatched flat in one message; 2+ platforms, or ~8+ criteria with 3+ lanes, get `qa-lead`. Review: a `graph-control depth` panel with more than ~2,000 changed lines or ~120k diff tokens gets `reviewer-lead`; any other panel gets one reviewer with an explicit lens list and mandatory blocker reproduction. Leads are dispatched only at depth 1, and leaves never have the Agent tool. A lead runs its children in the foreground, since a background child is re-woken only when its lead is idle. The owner's settings pin `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2`, which `/graph-init` proposes. The ledger copies each lead's returned child ids and report paths.

   **Failures.** On a transient 5xx, 529 or 429, re-dispatch the task fresh from on-disk artifacts (its brief, partial report and diff), at most 3 attempts, one ledger row each. On the first 429, stop new fan-out, checkpoint the ledger, notify the owner with the reset time when the error states one, and resume with `--resume <run-id>`. No heartbeat nudges: stalled agents show in the status line (`graph-control status --line`).

   **Estimate and actuals.** At the plan gate, print one line: agents by role times the role medians from `python3 <plugin-root>/scripts/session_usage.py --start <30 days ago> --end <now> --medians` (the last 30 days), plus wall time from the wave count, as `estimate: <n> implementer, <n> reviewer, <n> qa = <tokens>; <waves> waves, ~<hours> h wall time`. At the merge gate, `merge.md` prints the actuals from the same script with `--run <run8>` over the run's window. Actual tokens or wall time over 2x the estimate opens a decision card.

   **Before implementation.** Run `validate-plan <run>/plan.json`, complete the bound run manifest, then run `preflight <run>/run.json --profile <profile> --graph <run>/graph.md --readiness-only`. Planning and its prerequisite research/design produce these inputs; implementation cannot start until both validators pass. Dispatch consumers only after their producers' contract checks pass. Record each check through `record-receipt <run>/run.json <receipt.json> --store <run>/receipts.json`; before presenting the merge gate, run `verify <run>/run.json --store <run>/receipts.json`. Commands use `uv run <plugin-root>/scripts/graph-control.py`. Receipts must bind the exact revision and dirty tree, runtime/fixtures/schema and executed cases; a source or contract change invalidates affected evidence. Reviewer and QA identities must be independent of implementers. Required test reports must include assertions and all expected case IDs with no skipped required cases.

5. **Honor gates.** A node with `gate: yes` stops and presents, for the owner's approval before anything downstream runs: its artifact; the ledger's `playbook:` line (which playbook, and why); at the plan gate, `goal.md`'s `ui:` line and - when `design` ran - the plan's `## Experience` section with its as-is and to-be images shown, not linked, since this is where the owner approves where things go, plus any interactive render it names. When the designer left `design/claude-design-brief.md` and this session has a Claude Design connector (tools named `mcp__claude_ai_Claude_Design__*` or `mcp__claude-design__*`), run the brief, link the canvas in the exhibit and add the link to `design/experience.md` before the first UI task commits it; otherwise say it was skipped; and at the merge gate, qa's verdict line verbatim - `PASS`, or `PASS (static-only)` with the skipped live steps listed, so an infra run verified without a cluster never looks like one verified with one.

   **Merge exhibit.** The merge node is `agent: engine`: the engine renders the exhibit itself into `.graph/<run>/merge.md`, with no planner dispatch. It holds the diff summary (`git diff --stat <base>..HEAD` grouped by plan task, using each task's `writable_paths` from `plan.json`); the review and qa verdict lines verbatim; the ux-evidence before/after pairs inline, when the run has them; `followups.md` as `## Follow-ups`; and what was parked (blocked legs, findings that survived the fix loop, skipped nodes with their reasons). The same file is the PR body in step 9.

   **Decision cards.** A question for the owner is a card, not a blocking ask. Append it to `.graph/<run>/decisions.md`, one line each: `- [ ] D<n> <what> | why owner: <..> | default: <..> | cost of waiting: <..> | reversible: yes|no | meanwhile: <..> | redo if other: <..>`. For a reversible card, apply the default, mark it `- [x] ... (default applied)`, and keep running. For an irreversible card, park only that leg; every other ready node keeps running. Read owner context lazily, only when a question is about to go to the owner. When the profile sets `ownerAccess: <path>`, inject that file into planner and spike briefs. Ask first, always, for spend, public posting, deletion, production writes, destructive operations, credentials, the first publish of a new public page, and messages to real people.

   **Gates by class.** `gates.owner_classes` and `gates.auto_classes` name risk row ids, plus `none` for a diff that matches no risk row. The merge gate is auto-approved only when all four hold: (a) every risk row reported by `graph-control depth --root <run worktree> --base <run base> --profile <profile> --plan <run>/plan.json` (JSON field `risk_rows`, which carries `outside-the-run` when a changed path matches no task's `writable_paths`; treat an empty list as `none`) is in `auto_classes` and none is in `owner_classes`; (b) `graph-control findings <run>/findings.json <run>/qa-findings.json --counts` returns blocking 0 and important 0 (an absent file is BLOCKED, not zero); (c) qa's verdict is a full PASS, and `PASS (static-only)` from an infra run without a throwaway cluster does not qualify; (d) `verify` passes. The template default for `auto_classes` is `[]`, so the owner merges everything until a repo opts in. `merge.md` records which condition held or failed.

   `--auto-merge` keeps its per-run meaning: it relaxes only the merge gate, only for this run, whatever the classes, and only when (b), (c) and (d) hold.

   **Notifications.** If the host exposes a push-notification tool, send only on transitions (NEEDS YOU becomes non-empty; run finished or failed; first 429), and only from a turn that already happens; never start a turn to notify.

6. **Handle NEEDS_SETUP.** If an agent reports it, stop that leg and tell the owner which skill or dependency is missing. Do not re-dispatch without it, and do not let the agent improvise the competency. A result produced without the house patterns looks the same as one produced with them, which is precisely the danger.

7. **Fix loop.** The fix node takes every input the two legs produce: each blocking and important finding in the reviewer's `findings.json` and in qa's `qa-findings.json` (for example Schemathesis spec drift), and each `FAILED` qa row (its reproduction steps are the bug report). Before each re-run, keep the round: rename `findings.json`, `qa-findings.json` and `qa.md` to `*.r<N>.*` (round 1 = the first review), so the next round writes fresh files and `retro` can see what every round caught, not only what survived. Each round is a FRESH dispatch of the tier that built the task, never a resumed agent: its inputs are the brief, the findings file paths and `git diff <last reviewed head>..HEAD`. SendMessage the original author only for findings marked `needs_author_context: true` (the field arrives with the findings schema in `review-protocol`). Round 3 moves up one tier: a small task goes to `implementer`, and a standard task stays on `implementer` but requires a fresh diagnosis first (`superpowers:systematic-debugging` REQUIRED, a new hypothesis in `attempts.json` before any edit). Then re-run every node that feeds `fix` - the reviewer's node, whose input is the open blocking and important findings plus the fix-commit diff, not the whole branch, and the qa-agent node (`qa`, or `verify` in the infra playbook) for the rows that failed, any row whose files the fix touched, and every check that produced a finding in the previous round's `qa-findings.r<N>.json` (Schemathesis drift re-runs Schemathesis) - so the fresh `qa-findings.json` says whether each one is gone rather than silently dropping it. At most 3 rounds. Record each attempted fix, hypothesis, evidence and result in `attempts.json`; run `validate-attempts` before another attempt. Two failed attempts on the same hypothesis require fresh diagnosis or a plan change before continuing. Do not repeat the same command or broaden tests without a changed input, a failure to investigate or unresolved evidence. Surface anything that survives as a labelled list for the owner. Nits never block.

   A repo whose profile sets `runtime.none` still runs the qa node; qa verifies through the public surface instead of a stood-up stack, so this rule does not trap libraries and CLIs. A qa `BLOCKED` is not a fix-loop input: the system could not be stood up, which is a missing `runtime` block, seed or env, not a code defect. Treat it like `NEEDS_SETUP` (step 6) and name what is missing. The merge gate does not open on a run whose qa leg never ran. A `design` node's `BLOCKED` (a configured `runtime` that would not come up for the as-is captures) is handled like `NEEDS_SETUP` (step 6) too: mark it `blocked: <what>`, tell the owner what is missing, and `--resume` re-runs it - never design blind, and never let `plan` run without it.

8. **Keep the coordinator compact.** Children write full logs and findings to artifacts and return at most 1,500 tokens plus artifact paths: status, source identity, changed case results, blocker. A reviewer returns one verdict line plus the findings path. The engine reads files and never relays a child's prose into another dispatch; the next dispatch gets the path. A child that is only waiting never messages main, and the engine does not reply to one. Coalesce repeated running/progress/yielded notifications by task and event ID; update status without a new reasoning turn where the host supports it. Wake the coordinator for completed, failed or decision-required events. Host-mandated wakeups may still occur; record them as overhead rather than claiming suppression. Reuse accepted evidence by exact source/contract identity; never copy the entire session into a child.

   **Update the ledger after every node:** status, artifact path, timestamp. Follow-ups live beside it in `.graph/<run>/followups.md` (written by the plan node, appended by implementers); the engine never rewrites that file, and the merge node reads it. This is what lets a run survive compaction and what `--resume` reads. Trust it over your own recollection of what you did.

9. **After the merge gate.** Approval and merging are two ledger states. The profile's `integration: pr | push-main` (default `pr`) picks how approved work lands:
   - **`approved`** - the owner approved the merge gate, or step 5 auto-approved it.
     - `pr`: the engine pushes the run branch and opens the PR with `gh pr create` if none exists (body: the merge exhibit - diff summary, evidence, `## Follow-ups`), and records its number. Where the repo has CI, the run branch must be green before merge. When step 5 auto-approved the gate, the engine is the one that merges: `gh pr merge <n> --merge`.
     - `push-main`: from the run worktree, fetch and rebase on origin/<default>; a conflict stops and becomes a decision card. Assert the target branch: `<default>` is origin's default branch and the rebased HEAD descends from origin/<default>. Push `HEAD:<default>` (`git push origin HEAD:<default>`), find the CI run for the pushed SHA (`gh run list --commit <sha> --json databaseId`), then start `gh run watch <id> --exit-status` with run_in_background and report its result when it exits. Red CI is a decision card, never an automatic revert.
   - **`merged: <sha>`** - the change is on the default branch. The engine checks with `gh pr view <n> --json state,mergeCommit` (or, for `push-main` and off GitHub, `git merge-base --is-ancestor <run branch head> origin/<default>` after a fetch) and records the merge commit SHA, which `post-deploy` waits to see serving.

   The `post-deploy` node needs `merged:`. If the owner has not merged yet, mark it `waiting: merge` and stop; `--resume <run-id>` checks again. An empty `deploy.wait` makes it `SKIPPED` and the run goes on to `retro`. A post-deploy `FAIL` is never a fix-loop input and never triggers an automatic rollback: its rollback recommendation goes to the owner at once.

10. **Retro, then report.** Retro fast path: when every round's findings files (`findings.json` and each `findings.r<N>.json`) and qa findings files (`qa-findings.json` and each `qa-findings.r<N>.json`) hold zero blocking or important findings (each file present; an absent file is not zero findings), no qa row was `FAILED` in any round, no `NEEDS_SETUP` or `BLOCKED` stop happened, and post-deploy is not `FAIL`, the engine writes a one-line `.graph/<run>/retro.md` - `No leaks: <n> review rounds, <m> qa rows verified` - marks the retro node `done (fast path)` and dispatches nothing. Otherwise it dispatches the `retro` agent.

    **Report.** The full report goes to `.graph/<run>/run-report.md` (not `report.md`, which is the bug playbook's input): the run id, each node's status, the gate verdicts, the post-deploy verdict, and the retro's proposed rule changes as diffs for the owner to apply or decline. The engine applies none of them. Deliverables go to a durable repo path, never only to chat or a scratchpad.

    **Reply contract.** Status and decision replies to the owner take at most 5 lines, in plain words, echoing the owner's choices back: what I did, what I need from you, and one recommended action. No internal codes, node ids or SHAs unless asked; point to the report for the rest.
